# 部署说明：夜间自动更新 + GitHub Pages

本文档说明仓库里的自动更新工作流 `.github/workflows/scheduled.yml` 怎么用：需要往仓库里上传哪些缓存文件、怎么第一次启用 GitHub Pages、可选的发布地址变量、本地怎么手动跑，以及常见问题。

---

## 一、这套流程做什么

工作流每天 **UTC 16:00 = 北京时间 00:00**（`cron: '0 16 * * *'`，Asia/Shanghai 无夏令时）自动运行一次，也可以在北京时间任意时刻手动触发。执行顺序：

1. **检查缓存**：确认仓库 `cache/` 目录里有必需的历史缓存文件；缺文件时只输出醒目提示并跳过后续所有步骤（定时任务会显示为绿色，不会报红）。
2. **`ahshgb check`**：校验缓存文件可读、格式正确。
3. **`ahshgb update`**：从阿基米德接口/CDN 增量探测最近 `120` 天的整期回听，把新出现的节目写入 `cache/`（缓存里已有的日期会跳过）。这一步失败**不会**阻断后续流程，仍会用现有缓存构建站点。
4. **提交 `cache/` 变更**：只有 `cache/` 真的产生 diff 时才提交（提交者身份是 `github-actions[bot]`）；push 前先 `git pull --rebase` 同步远端，最多重试 3 次。
5. **`ahshgb build`**：从 `cache/` 重建 `site/ahshgb.opml` 与每个节目一个的 `site/feeds/*.xml`。
6. **`ahshgb stats`**：统计缓存数据，写入本次运行的 Step Summary（仅展示用）。
7. **部署 GitHub Pages**：把 `site/` 作为 Pages 产物上传并部署，环境为 `github-pages`。

每次运行的详细输出在 Actions 运行页面的 **Summary** 标签里（Step Summary），包括 update / build / stats 的关键日志和最终任务结果表。

> 工作流文件必须在默认分支上，`schedule` 定时触发才会生效；手动 `Run workflow` 可以选择分支运行。

## 二、需要上传到 `cache/` 的文件

仓库的 `cache/` 目录是本项目的数据来源：阿基米德接口只提供“当前在播/可回听”的节目信息，历史回听地址需要靠听友上传的历史缓存来保留。

| 文件 | 是否必需 | 说明 |
| --- | --- | --- |
| `cache/probe_cache.csv` | **必需** | 探测结果缓存：每个 `(c_id 桶, 日期, 时段)` 是否可读（200/206=可读、403=归档锁、404=无文件）。工作流每晚在其基础上增量追加，已命中的记录会跳过 |
| `cache/roster.json` | **必需** | 节目与阿基米德 `c_id` 桶标识的对应关系，决定要探测哪些节目、哪些时段 |
| `cache/discovery.json` | 可选 | 节目发现映射（用于自动发现新节目/新桶） |
| `cache/ahrtv_episodes.json` | 可选 | 安徽广播电视台（ahrtv.cn）补源节目缓存，主要覆盖 2020-01-01 ~ 2022-10-14 窗口 |
| `cache/programs.json` | 自动维护 | 每晚从阿基米德接口刷新的“在播节目 → 桶/时段”映射，由程序写入并随缓存一起提交，**不用手动准备** |

> 旧流水线里的 `ajmide_episodes.jsonl`（由 probe_cache 派生的中间清单）本仓库**不需要**，上传了也不会被读取，可以只保留在本地。

上传方式（二选一）：

- **网页上传**：仓库页面 → `cache/` 目录 → `Add file` → `Upload files`，把文件拖进去，提交到默认分支。
- **命令行**：

  ```bash
  git add cache/
  git commit -m "chore(cache): 上传历史回听缓存"
  git push
  ```

注意事项：

- **不要**上传 `site/`、`.tmp/`、`download/`、`ajmide_download/`、`ahrtv_download/` 等构建产物或音频文件，`.gitignore` 已经把常见产物忽略；`*.part` 临时文件也会被忽略。
- 必需文件缺任意一个，工作流都会走“优雅跳过”分支：只发警告、跳过更新/构建/部署，不报错。补齐后等下一次定时任务，或手动 Run workflow。
- GitHub 对单个文件有 **100 MB** 硬限制，超过会导致 push 失败。缓存都是纯文本，正常远小于这个量级；如果仓库里已有特别大的历史缓存，建议先精简再传。
- 缓存文件是公开仓库的一部分，上传即公开。请只上传本项目需要的节目元数据/地址，不要上传含版权的音频内容。

## 三、首次启用 GitHub Pages

1. 打开仓库 **Settings → Pages**。
2. 在 **Build and deployment → Source** 下拉框里选择 **GitHub Actions**（不要选 “Deploy from a branch”）。
3. 回到 **Actions** 页面，选择左侧的 `定期更新任务`，点 **Run workflow**（workflow_dispatch）手动跑一次，确认绿色通过。
4. 运行结束后，`Settings → Pages` 会显示站点地址，形如 `https://<用户名或组织>.github.io/<仓库名>/`。
5. 确认能打开 OPML：浏览器访问 `<站点地址>/ahshgb.opml`。本项目当前仓库（`TaoEngine/ahshgb-forever`）的默认 Pages 地址是 `https://taoengine.github.io/ahshgb-forever/`，OPML 即 `https://taoengine.github.io/ahshgb-forever/ahshgb.opml`（已写入 README）。

首次部署后可能需要等几分钟 Pages 才生效；如果 `configure-pages` 步骤报 `Get Pages site failed` / `Not Found`，基本就是 Pages 还没按上面的方式启用。

## 四、可选仓库变量 `PUBLIC_BASE_URL`

产物（`ahshgb.opml`、各 RSS feed）里的链接是**绝对地址**，由构建时传入的 base URL 决定。工作流按下面的规则取地址：

1. 仓库变量 `PUBLIC_BASE_URL` 非空 → 用它；
2. 否则回退到 README 约定的 `https://taoengine.github.io/ahshgb-forever`。

**什么时候需要设置它**：当仓库真正的 Pages 地址不是 `https://taoengine.github.io/ahshgb-forever` 时（例如仓库改名、迁移到组织账号，或使用了自定义域名），就必须设置，否则 OPML 里的 `xmlUrl` 会指向不存在的域名，播客客户端无法订阅。

设置方法：

1. 仓库 **Settings → Secrets and variables → Actions**。
2. 切到 **Variables** 标签页 → **New repository variable**。
3. Name 填 `PUBLIC_BASE_URL`，Value 填站点根地址（**不要**带结尾斜杠，带了也会被自动去掉），例如：
   - `https://taoengine.github.io/ahshgb-forever`（当前仓库默认地址，一般不用设）
   - `https://<组织>.github.io/<仓库名>`
   - `https://ahshgb.example.com`（自定义域名）
4. 保存后重新跑一次工作流（手动 Run workflow 即可），产物里的链接才会更新；已经部署的旧产物不会自动改。

> 仓库变量不是 secret，值会出现在日志里，公开地址没有泄露风险。

## 五、本地手动运行

前提：Python **3.13**（与仓库根目录 `.python-version` 一致），项目**零依赖**，**不需要** `pip install`、`requirements.txt` 或 `setup.py`。所有命令都从**仓库根目录**执行：

```bash
# 1. 校验缓存文件是否齐全、可读
python -m ahshgb check --cache-dir cache

# 2. 增量探测最近 120 天（8 个并发，缓存已有点会跳过）
python -m ahshgb update --cache-dir cache --days 120 --workers 8

# 3. 从缓存重建站点（--base-url 换成你的实际发布地址）
python -m ahshgb build --cache-dir cache --out site --base-url "https://taoengine.github.io/ahshgb-forever"

# 4. 查看缓存统计
python -m ahshgb stats --cache-dir cache
```

本地产物在 `site/` 下（`.gitignore` 已忽略，不会误提交）。想本地预览可以用：

```bash
python -m http.server 8000 --directory site
# 浏览器打开 http://localhost:8000/ahshgb.opml
```

只想用现有缓存重建、不做增量探测时，跳过第 2 步即可；工作流手动触发时勾选 `skip_update` 等价于此。

## 六、产物说明

| 路径 | 说明 |
| --- | --- |
| `site/ahshgb.opml` | OPML 订阅清单，播客客户端导入这个地址。部署后地址为 `<base-url>/ahshgb.opml` |
| `site/feeds/*.xml` | 每个节目一个 RSS 2.0 订阅源（文件名是节目名的 hash，避免中文/特殊字符做文件名）。OPML 里用绝对 `xmlUrl` 引用它们 |
| `site/.nojekyll` | 关闭 Jekyll 处理；Actions 部署本身直接用产物，保留只是为了兼容 |

`site/` 每次都由 Actions 重新生成，不入库；**不要**把 `site/` 提交到仓库。

> 2020-01-01 ~ 2022-10-14 的 ahrtv 补源里，2020/2021 部分是 HLS（`.m3u8`）链接，enclosure 的 `type` 为 `application/vnd.apple.mpegurl`。部分播客客户端（如部分版本的 AntennaPod）不支持 HLS 单集，可能无法播放；这是历史数据源本身的限制，不是本工具生成的 URL 有问题。

## 七、手动触发参数

Actions → `定期更新任务` → **Run workflow**，有两个输入：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `days` | `120` | 增量探测最近多少天（正整数）。调大可以补更早的历史，但耗时更长 |
| `skip_update` | `false` | 勾选后**跳过**增量探测，只用仓库里现有的 `cache/` 重建并部署（只想改链接/发布地址、或阿基米德接口临时故障时用） |

## 八、常见问题

### 1. 缓存缺失：任务提示跳过、没有部署

- **现象**：日志出现 warning“缺少历史缓存”，Step Summary 里列出缺少的文件；后面的 update/build/deploy 全部跳过，但任务整体是绿色的（这是设计行为，避免定时任务每天报红）。
- **原因**：仓库 `cache/` 里没有 `probe_cache.csv` 或 `roster.json`（可能还没上传，或上传到了别的目录、文件名大小写不对）。
- **处理**：按第二节把必需文件上传到 `cache/`，然后手动 Run workflow 或等下一次定时任务。

### 2. `configure-pages` 失败 / Pages 未启用

- **现象**：`Get Pages site failed`、`Not Found` 之类错误，部署步骤没执行。
- **原因**：GitHub Pages 还没启用，或 Source 不是 “GitHub Actions”。
- **处理**：Settings → Pages → Source 选 **GitHub Actions**，保存后再跑一次。若是组织仓库，确认组织策略允许启用 Pages。

### 3. 定时任务延迟或没有按时跑

- GitHub 的 `schedule` 在整点高峰期会延迟，常见延迟几分钟到几十分钟，偶尔会跳过当次；另外仓库连续 60 天没有任何提交活动时，定时任务可能被自动暂停（会收到 GitHub 通知，点一下即可恢复）。
- `cron` 是 **UTC** 时间：`0 16 * * *` = 北京时间次日 00:00，不要写成 `0 0 * * *`。
- 需要立刻更新时直接 Actions → Run workflow 手动补跑即可。

### 4. 自动提交被分支保护拦截

- **现象**：`git push` 报 `protected branch`、`GH006: Protected branch update failed`、`Required status check ... is expected` 等；工作流在“提交缓存变更”步骤失败（连续 3 次 `pull --rebase`/`push` 重试后放弃），本次不会再构建部署。
- **原因**：默认分支开了分支保护（要求 PR / 要求状态检查 / 禁止直接 push），`github-actions[bot]` 不在允许名单里。
- **处理**（任选其一）：
  1. 在分支保护规则里允许 `github-actions[bot]` 推送，或把该规则配置为对 bot 放行（bypass）；
  2. 临时关闭该分支保护规则，跑完再打开；
  3. 如果必须保留保护，需要把工作流改成“创建 PR”的流程（当前实现是直接提交，不提供 PR 模式）。
- 缓存提交失败时，本次运行动态更新的缓存只存在于 runner 上、不会保留，下次会重新探测。

### 5. 增量更新失败，但任务继续

- **现象**：`增量更新缓存` 步骤有 warning“增量探测失败”，但后面的提交/构建/部署照常执行。
- **原因**：阿基米德接口或 CDN 网络抖动、限流、超时等。工作流特意设置 `continue-on-error: true`，保证即使探测失败也能用旧缓存把站点重新部署一次。
- **处理**：看 update 日志里的具体错误；稍后手动重跑，或用 `skip_update=true` 只重建；若持续失败，检查本地 `python -m ahshgb update` 是否也失败（接口/域名可能变化）。

### 6. push 报权限不足（403 / `Resource not accessible by integration`）

- 工作流已经声明了 `permissions: contents: write`。如果仍然失败，检查 **Settings → Actions → General → Workflow permissions** 是否为 “Read and write permissions”，以及组织/企业级策略是否限制了 `GITHUB_TOKEN` 的写权限。

### 7. 缓存文件过大 / push 被拒绝

- GitHub 单文件上限 **100 MB**，超过需要精简或拆分文件后再上传；仓库总量建议保持在 1 GB 以内。
- 历史缓存里冗余很多时，可以先在本地 `ahshgb stats` 看看规模，再决定清理策略。

### 8. 部署成功，但 OPML 里的订阅链接域名不对

- **原因**：`PUBLIC_BASE_URL` 没设置或填错（见第四节），产物里的绝对链接仍然指向默认地址。
- **处理**：设置/修改仓库变量后，手动 Run workflow 重新生成并部署，再让播客客户端用新的 OPML 地址重新导入。

### 9. `校验缓存` 步骤失败

- **现象**：`ahshgb check` 报错、任务变红，后续更新/构建/部署都没有执行。
- **原因**：`cache/` 里的必需文件存在但内容损坏、字段缺失、或者不是程序需要的格式（例如上传时被截断、编码被改成 UTF-16 等）。
- **处理**：看 check 日志里具体是哪个文件有问题（`probe_cache.csv` 里有非法日期/字段时 check 会报出被跳过的行数）；用本地 `python -m ahshgb check --cache-dir cache` 复现后重新上传正确的文件。只有文件真实存在却损坏时才会走到这里；文件缺失只会在“检查历史缓存”步骤被优雅跳过。

### 10. 构建失败：缓存里没有可播 episode

- **现象**：`站点构建` 步骤报 `缓存里没有可播 episode，拒绝生成空订阅源`，任务变红、部署跳过。
- **原因**：`cache/probe_cache.csv` 里没有任何可读命中记录（例如上传的是空模板、或条目全部过期/失效），程序拒绝生成空 RSS。
- **处理**：确认上传的是真实探测缓存；本地 `python -m ahshgb stats --cache-dir cache` 查看“可读命中”数量，必要时先跑一次 `ahshgb update` 再上传。
